## Story and outcome

As the owner, I want the server patched and locked down so that the platform sits on a secure base.

This story is split so it cannot lock out SSH. Part A (packages, SSH keys, fail2ban) runs first. Part B (UFW default deny, incoming only on `tailscale0`) runs only after [VME-005](VME-005.md) has a working Tailscale SSH session.

## Files in scope

- `scripts/bootstrap_server.sh` (idempotent functions for this story only; later S0 stories append their own functions)
- `docs/SERVER.md` (create; record what was verified)

## Do not touch

- Application source, Docker compose, NVIDIA packages, gocryptfs, Tailscale install (that is VME-005)
- UFW enablement before VME-005 is confirmed

## Acceptance criteria

- AC1: `sudo unattended-upgrades --dry-run` shows security updates configured to install automatically.
- AC2: Password SSH login is refused. Key login works. Root login is refused.
- AC3: After Part B, `sudo ufw status verbose` shows incoming default deny, outgoing default allow, and incoming allowed on `tailscale0`. Until VME-005 is done, AC3 stays open on purpose.
- AC3 note (D6): UFW does not govern ports Docker publishes later. This story must not claim it locks Docker down. That check is VME-405.

## Build steps

1. Confirm an SSH key session already works before changing `sshd_config`. Keep the current session open.
2. `sudo apt update && sudo apt full-upgrade -y && sudo apt install -y unattended-upgrades ufw fail2ban`.
3. Enable unattended security upgrades and record the config path in `docs/SERVER.md`.
4. In `/etc/ssh/sshd_config` set `PasswordAuthentication no` and `PermitRootLogin no`. Restart `ssh`. Prove password login fails from a second session before closing the working one.
5. Put steps 2–4 in `scripts/bootstrap_server.sh` as idempotent functions. Running the script twice must not duplicate lines or fail.
6. Part B, only after VME-005: from a working Tailscale session, allow OpenSSH on the LAN temporarily if it is not already allowed, then `sudo ufw default deny incoming`, `sudo ufw default allow outgoing`, `sudo ufw allow in on tailscale0`, `sudo ufw enable`. Confirm the Tailscale session still works. Then remove the temporary LAN allow. Record the final `ufw status verbose` in `docs/SERVER.md`.

## Tests and done when

Manual checks on the MSI, written into `docs/SERVER.md`: dry-run output summary, password-login refusal, and final UFW status. Part A can be marked done before Part B. The story is done when AC1–AC3 are all recorded.

## Challenges and decision

Enabling UFW with “only `tailscale0`” before Tailscale exists drops every LAN session, including the one doing the setup. Fail2ban can also ban the owner during repeated SSH tests. Whitelist the Tailscale subnet in fail2ban or pause the jail during the cutover, and write that down.

Decision: follow D1. Do not run Part B in the same sitting as the first bootstrap.
