## Story and outcome

As the owner, I want one place to see and enable agents, and a warning when one stops running.

## Files in scope

- `src/vme_orchestrator/watchdog.py`
- Agent routes in `app.py`: `GET /v1/agents`, `POST /v1/agents/{id}/run`, `POST /v1/agents/{id}/enable`, `POST /v1/agents/{id}/disable`
- `tests/orchestrator/test_watchdog.py`

## Do not touch

- The runner’s override file format (VME-110 already defined `{"disabled": [...]}`)
- Deal Scout feed staleness (VME-310 emits its own finding type)

## Acceptance criteria

- AC1: On startup and every 5 minutes, `GET` the runner `/v1/agents` with `VME_RUNNER_TOKEN` and upsert the `agents` table (id, tier, enabled, version, health fields).
- AC2: The management routes from section 6.7 work with the admin token. Disable writes `<runner data>/overrides.json` (D18) and calls the runner `POST /v1/reload` or disable path the runner actually exposes. Enable removes the id from `disabled`. State survives an orchestrator restart because it lives in that file and is re-read by the runner.
- AC3: Emit one `system` finding when an agent has 3 consecutive failures, or no success within 3× its interval, or the runner has been unreachable for 15 minutes. Dedup one per condition per 6 hours (`dedup_key` includes the condition and a 6-hour bucket). These findings go through normal intake and the router (D15: quiet hours and the daily cap still apply).

## Build steps

1. The watchdog’s own findings use a reserved agent id `system` and tier `public`, with no personal payload.
2. If the runner client is down, still emit the unreachable finding on the local orchestrator intake. Do not require the runner to post it.
3. `consecutive_failures` comes from the runner payload when present, otherwise from orchestrator bookkeeping updated by the sync.

## Tests and done when

Simulated stale agent, dedup inside 6 hours, a second alert after 6 hours, disable round-trip against a fake runner. pytest, ruff, mypy green.

## Challenges and decision

VME-110’s API has `POST /v1/reload` and per-agent run, not a dedicated enable route. This story can POST reload after writing `overrides.json`, which the runner reads on reload and on startup (D18). If reload is not implemented yet, add it in VME-110’s file only as the story allows: this story may edit `runner.py` solely to honor a reload re-read of overrides. Prefer calling the existing reload route.

System findings that fire while the data volume is locked never fire. That is master plan risk 9. Do not add a second notifier that bypasses the lock.

The “feed stale” clause in the master plan’s watchdog sentence is Deal Scout’s `feed_health` finding (VME-310), not a second implementation here. This story’s AC3 list is failures, missed interval, and runner down.
