## Story and outcome

As the owner, I want personal data encrypted at rest so that a stolen laptop, while locked or powered off, does not expose it.

## Files in scope

- `scripts/unlock.sh`
- `scripts/lock.sh`
- `scripts/bootstrap_server.sh` (package install and directory creation only)
- `docs/SERVER.md` (mount layout, passphrase handling, reboot result)

## Do not touch

- `docker/compose.yml` and the image entrypoint (VME-401)
- Real profile YAML, `.env` secrets, or the gocryptfs master key (paper, offline, never in git)

## Acceptance criteria

- AC1: After a reboot, `/srv/vme/data` is an empty mountpoint until `scripts/unlock.sh` runs.
- AC2: `unlock.sh` prompts for the passphrase, mounts gocryptfs, creates `/srv/vme/data/.unlocked`, and creates the data subdirectories (`config/agents`, `orchestrator`, `runner-net`, `ntfy`, `logs/squid`). It may call `docker compose up -d` only if `docker/compose.yml` already exists. Until VME-401, skip Compose and say so in the script output.
- AC3 from the master plan (Compose refuses to start without `.unlocked`) is VME-401, not this story (D5).

## Build steps

1. `sudo apt install -y gocryptfs`. Create `/srv/vme/.cipher`, `/srv/vme/data`, and `/srv/vme/models`. Models stay outside the encrypted mount (large, not personal).
2. `gocryptfs -init /srv/vme/.cipher`. Print the master key once and store it on paper. Do not write it into the repo, `docs/SERVER.md`, or the script.
3. Set `user_allow_other` in `/etc/fuse.conf`. `unlock.sh` mounts with `gocryptfs -allow_other /srv/vme/.cipher /srv/vme/data`. Without `allow_other`, dockerd cannot see the files.
4. `unlock.sh` then `touch`es `/srv/vme/data/.unlocked` and `mkdir -p`s the subdirectories listed in AC2. Prompt via the terminal. Do not accept the passphrase as a command-line argument (it would land in the process list and shell history).
5. `lock.sh` runs `docker compose down` when the compose file exists, then `fusermount -u /srv/vme/data` (or `fusermount3`). If the mount is busy, exit non-zero and name the holder. Do not force-unmount.
6. Reboot. Confirm AC1, then unlock and confirm the directories exist.

## Tests and done when

The reboot test is written in `docs/SERVER.md`: locked path listing, unlock command result, and a note that AC3 waits on VME-401. Scripts are idempotent: unlock on an already-mounted folder exits 0; init is not run twice.

## Challenges and decision

Manual unlock after every reboot is an accepted tradeoff (master plan risk 9). The watchdog cannot run while the disk is locked. Tailscale reachability is the “machine is up but locked” signal.

FUSE mounts often show as empty inside containers when `allow_other` is missing. That looks like data loss. Decision D5 requires the flag now, before VME-401, so the first Compose up sees the files.

`.unlocked` as a bind-mount source must be a real file before Compose starts. Creating it in `unlock.sh` is what makes VME-401’s bind mount valid.

`/srv/vme/models` is unencrypted on purpose. Do not move Ollama models into `.cipher`.
