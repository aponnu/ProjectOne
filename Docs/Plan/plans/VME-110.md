## Story and outcome

As the platform, I want a runner that schedules agents and isolates failures so one agent cannot stop the others.

## Files in scope

- `src/vme_core/runner.py`
- `src/vme_core/client.py` (orchestrator client used to post findings)
- `tests/core/test_runner.py`

## Do not touch

- Orchestrator route implementations (VME-201+). The client talks to a mocked URL.
- Deal Scout

## Acceptance criteria

- AC1: `vme-runner --tiers public,private` starts FastAPI on port 8100 and an `AsyncIOScheduler` with one job per enabled agent: `max_instances=1`, `coalesce=True`, `misfire_grace_time=300`, jitter from the manifest.
- AC2: Each run calls `budget_reset()`, applies `asyncio.timeout(timeout_seconds)`, catches exceptions, and writes a `runs` row in `<data>/runner.db`: `agent_id`, `started_at`, `finished_at`, `status`, `error`, `findings_emitted`, `items_seen`, `notes` (JSON, default `{}`; D10). Findings are posted to the orchestrator in batches of at most 100, retried 3 times, then stored in an outbox table and retried on a later tick.
- AC3: Internal routes from master plan section 6.7 exist and require `Authorization: Bearer <VME_RUNNER_TOKEN>` (D17). Wrong or missing token is 401 with an empty body. Routes: `GET /v1/agents`, `POST /v1/agents/{id}/run`, `POST /v1/agents/{id}/feedback`, `POST /v1/reload`.
- AC4: `POST /v1/agents/{id}/feedback` calls `on_feedback`. An exception is logged and returns 500. The process stays up.
- AC5: `agent.setup()` runs once at load. A setup failure disables that agent and marks it unhealthy. Other agents still load.
- AC6: SIGTERM stops the scheduler and waits up to 30 seconds for the current run.
- D18: on startup, read `<data_dir>/runner-net/overrides.json` if it exists. Shape: `{"disabled": ["agent_id"]}`. Disabled agents are not scheduled. A missing file means all discovered agents are enabled.

## Build steps

1. Catch `FindingValidationError` from `emit`, log it, and continue the run (see VME-108). Do not fail the run for one bad finding.
2. Outbox rows store the finding JSON and a retry count. A successful post deletes them. Posting is idempotent on the orchestrator side (VME-202, D13); the runner still sends the same finding ids again.
3. `GET /v1/agents` returns id, tier, enabled, health, last run, and `extra: {}` so VME-312 can add mute data later without a new route.
4. `notes` from `RunResult.notes` is stored on the row (D10).
5. Bind host `0.0.0.0` inside the container is fine because the port is not published (Compose, VME-401). Do not publish 8100 in this story.

## Tests and done when

Fake agents: success, raise, timeout, setup failure. Outbox resend when the orchestrator mock returns 500 then 200. Auth rejected without a token. Overrides file disables one agent. pytest, ruff, mypy green. No real network.

## Challenges and decision

APScheduler 3.x and the FastAPI lifespan must share one event loop. Start the scheduler in lifespan, shut it down in the same lifespan. Do not create a second loop.

The master plan says validation errors are logged and the run continues, while also saying an agent exception fails that run only. `FindingValidationError` is the continue path. Any other exception fails that run and is recorded. Timeouts are a failed run.

`overrides.json` lives under the runner data dir, which VME-401 mounts at `/data`. The path in D18 includes `runner-net` because that is the on-disk folder name. Inside the container `VME_DATA_DIR=/data` already points at `runner-net`, so the file is `/data/overrides.json` in the container and `/srv/vme/data/runner-net/overrides.json` on the host. Use `data_dir / "overrides.json"` in code. The review’s host path and the in-container path are the same file.

Shared runner token (D17) means a stolen runner token can also trigger runs. Accepted for v1. Do not invent a second token in this story.
